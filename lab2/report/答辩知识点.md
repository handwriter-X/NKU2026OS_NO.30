## 2. 开场怎么讲：本实验和你的职责

**本实验解决什么？**

> 先用启动页表让内核在高虚拟地址执行，再从设备树取得物理内存范围，建立每个物理帧的 Page 描述符，把排除固件、内核和描述符后的完整页交给分配器。页分配器提供连续页，简化 SLUB 再在页内分配小对象。

**你负责什么？**

> 我负责 C：核对 A/B 交付和接口，维护分页接入后的构建及测试工具，验证启动映射和内存分配，在宿主与客户机两层 GDB 中观察 QEMU 的 MMU/TLB，最后汇总报告和证据。已经合并的 PR 只核查历史，没有重复合并。

真实工作链：

```text
复位 ROM → OpenSBI → 0x80200000 物理 kern_entry
→ 写 satp → sfence.vma → 高地址栈与 kern_init
→ 清 BSS → dtb_init → pmm_init
→ 管理器 init → page_init → init_memmap
→ run_selftests → 空循环
```

必须分清：PMM 决定“物理页归谁使用”；页表决定“某个 VA 怎样访问 PA”。`alloc_page()` 本身不创建新映射；本实验用已经建立的直接映射访问分配到的页。

## 3. page_init：截图中第一个核心问题

位置：[pmm.c](../code/kern/mm/pmm.c)。外层 `pmm_init` 负责选择管理器、初始化管理器，再调用 `page_init`。本实现的 DTB 已由 `kern_init` 提前解析，page_init 读取解析结果。

**30 秒口述答案：**

> page_init 把探测到的连续 RAM 转换成分配器可以管理的空闲物理页：先计算管理上界，确定 Page 数组大小和位置，排除固件、内核和 Page 数组自身占用，把描述符先全部设为保留，最后只把完整空闲页交给 init_memmap。

按源码顺序掌握：

1. `get_memory_base/get_memory_size` 取得 DTB 解析结果，检查起点、容量和加法溢出。
2. `managed_end = ROUNDDOWN(min(base+size, PHYSTOP), PGSIZE)`。
3. `npage = managed_end / PGSIZE`，设置高地址直接映射偏移。
4. `desc_va = ROUNDUP(end, PGSIZE)`，即内核末尾后第一个整页地址。
5. `desc_pa = desc_va - va_pa_offset`，`count = npage-nbase`。
6. 检查 count 个 Page 能放进受管内存，令 pages 指向数组。
7. `desc_end = desc_pa + count*sizeof(struct Page)`。
8. `free_begin = ROUNDUP(desc_end, PGSIZE)`，避免描述符与可分配页重叠。
9. 清零数组，先将所有 Page 设为 reserved，并初始化每个 page_link。
10. 若 `free_begin < managed_end`，将相应连续页交给当前管理器的 `init_memmap`。

**常见追问：**

- 为什么先 reserved？保守初始化，只将确认可用的完整页解除保留，可避免误分配固件和元数据。
- 为什么描述符也占 RAM？它们是内核实际读写的元数据数组，不存在免费存储空间。
- 为什么数组起点和空闲起点都向上对齐？前者方便布局，后者保证不把描述符末尾所在的半页交出去。
- 为什么终点向下对齐？尾部不足一页的空间不能当作完整物理页分配。
- 没有完整空闲页怎么办？不调用 init_memmap；当前启动还要求有空间放描述符，错误布局会先被断言拒绝。
- 它是在“初始化页表”吗？不是；它建立物理帧描述符和空闲资源状态，启动页表已在 entry.S 准备好。

## 4. npage、nbase、pages 与地址换算：必须会手算

### 4.1 四种对象不要混淆

| 名称 | 含义 | 例子 |
|---|---|---|
| PA | 客户机物理地址 | 0x80411000 |
| KVA | 内核访问该物理位置的虚拟地址 | 0xffffffffc0411000 |
| PFN/PPN | 物理页号，即 PA 除以 4096 | 0x80411 |
| `struct Page *` | 描述该物理页的元数据地址 | `pages + (0x80411-nbase)` |

`Page *` 是描述符指针，不是那一页数据的起始指针；PTE 又是另一种描述 VA→PA 映射的页表项。

### 4.2 三个变量的准确含义

```text
PGSIZE = 4096 = 2^12
nbase  = DRAM_BASE / PGSIZE = 0x80000
npage  = managed_end / PGSIZE              # PFN 的排他上界
count  = npage - nbase                    # 描述符个数
pages  = Page 数组的首地址                 # 一个高虚拟地址指针
```

128 MiB 配置时：

```text
DRAM_BASE  = 0x80000000
managed_end = 0x88000000
nbase = 0x80000 = 524288
npage = 0x88000 = 557056
npage-nbase = 0x8000 = 32768
```

**不要回答 npage=32768。**本项目 npage 是绝对物理页号上界，32768 是页数。pages 覆盖受管范围内的保留页和可用页，不仅覆盖空闲页。

### 4.3 公式、单位和推导

以下公式针对合法描述符、合法受管 PA 及本实验的高地址直接映射：

```text
index = p - pages
PFN   = index + nbase
PA    = (p - pages + nbase) * 4096

p     = pages + (PA/4096 - nbase)
KVA   = PA + va_pa_offset
PA    = KVA - va_pa_offset
page2kva(p) = KADDR(page2pa(p))
```

截图中“用 n 配置和 n 贝斯算物理地址”，核心是 **描述符索引 + nbase**。npage 用于边界检查，不是 page2pa 中要加的基址。

`p-pages` 是相隔多少个 Page 元素，已按 sizeof(Page) 除过，不能再除以 4096。实际源码先用整数地址检查数组边界和元素对齐，再计算索引，避免非法描述符进入换算。

例子：`p = pages+1024`：

```text
index = 1024 = 0x400
PFN   = 0x80000 + 0x400 = 0x80400
PA    = 0x80400000
KVA   = 0xffffffffc0400000
```

这里 p 本身的数值并不等于 KVA；一个指向元数据，一个指向页内容。

`p+1` 移动 sizeof(Page)=56 字节，表示下一个描述符；`page2pa(p+1)` 比 page2pa(p) 增加 4096 字节。`pa2page` 使用 PA/4096，因此非页对齐 PA 也对应其所在帧，但 page2pa 返回的是帧起点，会丢掉原来的页内偏移。

### 4.4 va_pa_offset 为什么是这个数

```text
内核链接 VA = 0xffffffffc0200000
内核装载 PA = 0x0000000080200000
偏移 VA-PA  = 0xffffffff40000000
```

> 偏移是在已建立的直接映射区内换算 KVA/PA 的常量。减偏移只是软件计算，不是 MMU 的通用查页表过程，也不能用于任意用户地址或恒等映射别名。

PADDR/KADDR 在本项目还检查受管范围。256 MiB 时 DTB 可能位于管理上限外，dtb_init 用覆盖 1 GiB 的启动映射加常量偏移访问，不能误用只允许受管 PA 的 KADDR。

## 5. 内存布局：从 0x80000000 讲到空闲区

以下数值来自既有 Best-Fit/128 MiB 记录，内核大小变化后应以符号与新日志为准：

```text
0x80000000 ┌ 固件保留区：沿用课程约定，大小 2 MiB
0x80200000 ├ 内核镜像、数据、BSS，以及末尾对齐空间
0x80251000 ├ Page 描述符数组
0x80411000 ├ 完整空闲页区
0x88000000 └ 受管内存末端（不含）
```

能手算这些数：

```text
描述符个数 = 32768
sizeof(Page) = 56 字节
描述符空间 = 32768*56 = 1835008 = 0x1c0000 = 1.75 MiB
空闲页数 = (0x88000000-0x80411000)/4096 = 31727
```

前 2 MiB 保留的是平台/课程区域，不等于本次 OpenSBI 文件刚好有 2 MiB。DTB 本身也不等于 RAM；它是一段描述硬件的二进制数据。本实现校验 FDT 保留表终止项，但没有建立通用固件 reserved-memory 扣除器，因此不能宣称已正确管理任意真实硬件。

**128 MiB 管理上限与 1 GiB 映射范围是否矛盾？**不矛盾。映射描述地址可以怎样翻译，PMM 管理范围描述哪些实际 RAM 帧被纳入分配器；映射到某 PA 不代表那里有 RAM，更不代表那里允许分配。

## 6. Page、链表、container_of：截图中的细节题

### 6.1 Page 结构各字段

位置：[memlayout.h](../code/kern/mm/memlayout.h)。本机 GDB 对当前 ELF 的 `ptype /o struct Page` 实测如下：

| 字段 | 当前偏移 | 作用 |
|---|---:|---|
| ref | 0 | 预留引用计数字段；本实验未实现完整映射引用管理 |
| flags | 8 | reserved、property、allocated 等状态 |
| property | 16 | Fit 空闲块头的页数；Buddy 空闲块头的阶 |
| page_link | 24 | 内嵌双向链表节点，占 16 字节 |
| alloc_span | 40 | 完整分配头记录实际占用页数 |
| requested | 48 | 完整分配头记录原始请求页数 |

总大小 56 字节；字段间因 RV64 对齐存在填充，不能只把字段声明大小相加。共享头是唯一结构定义，A/B 不能各自定义不同的 Page。

状态掩码为 reserved=1、property=2、allocated=4；SLUB 另用 8 表示页归对象分配器使用。PageProperty 表示“有效空闲块头”，不是所有空闲页都有 property 标志。

**易错：Buddy 的 order=0 是合法一页块，不能用 property>0 判断它是否是空闲块头，必须看状态位。**

### 6.2 list_entry_t 的两个指针到底指什么

位置：[list.h](../code/libs/list.h)。

```c
typedef struct list_entry {
    struct list_entry *prev, *next;
} list_entry_t;
```

> prev/next 指向前后链表节点，不直接指向前后 Page 的结构体起点。Page 内嵌 page_link，链表操作只需要知道节点，访问 Page 时再做成员到宿主结构体的换算。

Fit 使用 `static free_area_t area`，其中 `area.free_list` 是哨兵节点对象，`&area.free_list` 才是头指针。链表里通常每个空闲块只挂块头的 page_link，不为块内每个页都挂一个节点。

```text
非空：head ⇄ A.page_link ⇄ B.page_link ⇄ head
空表：head.next = head，head.prev = head
```

**截图最后的问题：没有空闲块时指向哪？**

> 双向循环链表使用哨兵，空表的 next/prev 都指回头节点自身，判空是 head->next==head，不是 NULL。

只有一个元素时，head 的 next/prev 都指向该元素节点，该元素的 next/prev 都指回 head；不是该元素自身构成独立自环。

list_del 修改相邻节点的双向连接，并把删除节点初始化为自环。它只负责摘链，不会归还物理页或维护空闲页计数。已摘链节点自环也不自动代表它是空闲块。

### 6.3 从 page_link 恢复整个 Page

位置：[defs.h](../code/libs/defs.h) 的 to_struct、[memlayout.h](../code/kern/mm/memlayout.h) 的 le2page。

```c
#define le2page(le, member) to_struct(le, struct Page, member)
#define to_struct(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))
```

**口述答案：**

> 已知成员地址和成员在结构体内的固定偏移，用成员地址减 offsetof 就能得到结构体起点。这是侵入式链表常用的 container_of 思想。

当前 Page.page_link 偏移为 24，例如 Page 起点为 0x1000，节点在 0x1018，恢复时减 0x18。这个数应由 offsetof 计算，不应写死。

为什么先转 char*？按字节减偏移；若直接对 Page* 减 24，会减去 24 个 Page 的大小。

**不能把哨兵也传给 le2page**：哨兵是 free_area 的成员，不是 Page 的成员。遍历先比较 `at!=head` 再换算；这是正确性前提。

## 7. First-Fit、Best-Fit：会选、会拆、会合

### 7.1 指导书名称与当前函数的对应

不要在答辩现场只找 default_free_pages，却找不到当前实际实现：

| 指导书/转写概念 | 本仓库实际实现 |
|---|---|
| default_init | default_pmm.c 中 fit_init |
| default_init_memmap | fit_init_memmap |
| default_alloc_pages | first_alloc → fit_alloc_pages(n, false) |
| default_free_pages | fit_free_pages → insert_block |
| Best-Fit 分配 | best_fit_pmm.c 中 best_alloc → fit_alloc_pages(n, true) |

两种 Fit 共用地址有序链表及拆合逻辑，选块策略通过参数区别，不代表 Best-Fit 没有注册。

### 7.2 初始化与选块

fit_init：头节点自环，nr_free=0。fit_init_memmap：验证整段是 reserved，解除保留，将该区间登记为空闲块，并增加页数。

First-Fit 按链表地址顺序选第一个足够大的块；Best-Fit 选所有候选中最小的块，同尺寸保留先遇到的低地址块，精确匹配时可提前停止。

```text
空闲块按地址排列：低地址 A=8 页，高地址 B=4 页
请求 3 页：First-Fit 选 A，Best-Fit 选 B
```

地址有序不是大小有序；Best-Fit 的“最小”来自扫描比较，不是“拿链表第一个”。最优适应也不等于所有负载下性能最优，可能留下难用的小碎片。

### 7.3 从一段连续页拆出 n 页

选中块头 chosen，长度 L，申请 n：

1. 记录原长度 L，摘下原块头节点。
2. 若 L>n，余块头为 chosen+n，余块长度为 L-n，重新插入链表。
3. 标记前 n 个描述符已分配，清掉它们的空闲块属性。
4. 分配头记录 span=n、requested=n；空闲页数扣 n。

chosen+n 在 C 中移动 n 个 Page 描述符；因为元数据顺序对应连续物理帧，所以表示物理地址向后 n*4096 的那个页头，而不是对描述符指针直接加 n*4096。

### 7.4 free_pages 怎样释放并向前/向后合并

fit_free_pages 先验证整段范围及已分配状态，再清状态，按地址插入空闲块。

合并条件：

```text
前块连续：prev + prev->property == base
后块连续：base + base->property == next
```

“链表相邻”仅表示地址排序中的前后项，不保证物理连续，必须检查上面的等式。

前块连续时：长度加到 prev；摘掉 base 节点并清其块头属性；令当前块头变为 prev，再检查新的后邻居。后块连续时：长度加到当前块头，摘掉 next 并清其块头属性。

```text
释放前：[A 空闲 2 页][B 已分配 3 页][C 空闲 4 页]
释放 B → 与 A 合并为 5 页 → 再与 C 合并为 9 页
最终只剩 A 的块头节点
```

空闲计数只增加这次归还的 3 页；A/C 本来就是空闲的，合并时不能再把它们加一遍。合并改变块形状，不改变总空闲页数。

### 7.5 常见反问与改进

- 总空闲页数够，为什么申请失败？可能分散成多个小块，没有单个满足请求的连续区，属于外部碎片。
- 资源不足和非法调用怎样区分？合法但无法满足返回 NULL；零页请求、非法范围和重复释放触发断言。
- 重复释放如何阻止？pmm_mark_free 在改状态前验证整个范围的 allocated/reserved 状态，失败不应先改一半。
- Fit 能分批释放吗？本实现可以释放合法的已分配子区间；但不要对被部分释放的旧分配头再依赖完整分配跨度查询。
- 复杂度？选块 O(F)，F 是空闲块数；释放还涉及 O(n) 页状态验证/更新及 O(F) 插入，不能说整个 free 恒定时间。
- 怎样改进？next-fit 游标、按大小分桶、平衡树等；同时维护大小和地址索引可以兼顾搜索与合并，但提高实现成本。

### 7.6 使用 Best-Fit 到底改了什么

本实现 `pmm_init` 根据构建宏 PMM_BACKEND 选择 `default_pmm_manager`、`best_fit_pmm_manager` 或 `buddy_pmm_manager`。Makefile 默认 `PMM=best_fit`，对应 PMM_BACKEND=1。

`pmm_manager` 是函数指针表，包含 init、init_memmap、alloc_pages、free_pages、nr_free_pages、check。`alloc_pages(n)` 经过当前表分派；不是改一个输出字符串就切换算法。

```bash

make PMM=best_fit grade
make PMM=first_fit grade
make PMM=buddy grade
```

启动打印的管理器名称和策略区别测试一起确认选中了正确后端。构建目录按后端/测试场景隔离，避免复用错误宏配置的旧目标文件。

## 8. Buddy：扩展任务怎样讲、怎样证明

位置：[buddy_pmm.c](../code/kern/mm/buddy_pmm.c)。

**短答案：**

> Buddy 按 2 的幂次大小分阶。申请时向上取整，从更大的空闲块逐级拆分；释放时根据物理页号 XOR 找伙伴，只合并同阶、真正空闲且边界合法的伙伴。它简化拆合，代价是向上取整造成内部碎片。

order=k 表示 2^k 页。请求 5 页要取 order=3，实际占 8 页：requested=5、alloc_span=8，空闲数扣 8。释放仍调用 free_pages(p,5)，由分配头找回实际跨度；传 8、内部页或重复归还会失败。

```text
buddy_pfn = current_pfn XOR (1 << order)
buddy_pa  = buddy_pfn * 4096
```

必须是物理 PFN，而不是 Page 数组的相对索引；当前实现按绝对 PFN 对齐。合并还需检查伙伴范围、PageProperty 和相同 order，两个普通相邻块不一定是伙伴。

例子：8 页块对齐到 8 页边界。拆成两个 4 页块，再拆成两个 2 页块；两个相同父块的同阶子块才能合回。空闲区起点和总页数可能不是 2 的幂，因此 init_memmap 按 PFN 对齐、剩余容量拆成多个最大合法块，不假定一开始就是一个完整大块。

本实现 MAX_ORDER=15，理论最大块为 32768 页（128 MiB），但固件/内核占用和对齐约束使实际不一定存在这么大的可用块。

**如何展示：**

```bash
# Ubuntu，lab2/code
make PMM=buddy MEMORY=128M grade
```

应展示日志中的各阶边界、对齐和实际记账，以及递归合并/5→8 的通过项。真正执行的是 selftest.c 的 buddy_check，不是另有一个 Buddy 可执行程序。

**为什么测试有效？**隔离 8 页并占满其他可分配页，可以防止请求从别处成功掩盖拆合错误；同时核对实际跨度、物理对齐、空闲计数和独立占用位图。复杂度的分阶步骤约为 O(log P)，但本实现还逐页更新所有权状态，不能宣称整个调用无条件只有 O(log P)。

## 9. 简化 SLUB：对象分配与页分配的关系

位置：[slub.c](../code/kern/mm/slub.c)。

**短答案：**

> 第一层 PMM 分配页，第二层将页划为固定规格对象。小对象选择能容纳请求的最小规格，用空闲链分配，用 bitmap 记录占用；页内对象全部释放后，把整页归还 PMM。大对象直接申请连续页。

规格为 16、32、64、128、256、512、1024、2048 字节；每页前 128 字节是对齐后的头部，capacity=floor((4096-128)/unit)。例如 unit=16 时一页可放 248 个对象。bitmap 为 4 个 uint64_t，共 256 位，足以覆盖这个最大容量。

**必须能回答：**

- 申请 17 字节？使用 32 字节规格，浪费的 15 字节属于内部碎片。
- 对象空闲链的 next 存哪？写在空闲对象内部的起始指针位置；对象交付用户后不能再依赖那个旧 next。
- bitmap 为什么还要有？标记某个 slot 是否已分配，帮助识别重复释放和状态错误。
- 释放怎么找到 slab？PADDR 得到 PA，再 pa2page 找所在物理帧描述符，page2kva 返回页基址，读取该页头部元数据。
- 如何防内部指针？检查 offset 范围和 `(offset-HEADER_SIZE)%unit==0`，再检查占用位。
- 超过 2048 字节？申请 ceil((size+128)/4096) 页，返回页基址+128；头部记录原始请求页数。
- Buddy 后端会怎样？实际分配跨度可能大于请求，但释放仍传原始请求；Buddy 依据 alloc_span 归还实际页数。
- kmalloc(0)、kfree(NULL)？前者返回 NULL，后者不做事；与 alloc_pages(0) 的非法调用契约不同。
- 空页如何处理？从 cache 链摘下，清 magic，并 free_page 立即归还；没有完整 Linux SLUB 的 per-CPU、NUMA 或延迟回收。
- 能保证识别所有陈旧指针吗？不能。地址被重新分配后，单纯 bitmap 不能区分旧指针和新所有者；它不是完整的时间内存安全机制。

**展示：**

```bash
make grade
```

默认正常自测包含 slub_check。应指出两条 SLUB PASS，覆盖规格边界、16 字节对齐、大对象、数据隔离、600 对象跨页、交错释放/重用、空页归还和 OOM。三种 PMM 后端的正常场景都运行它。

## 10. DTB 与物理内存探测思考题

DTB 是 Flattened Device Tree 的二进制形式，由启动环境传给内核。本项目 a0 是 hart ID，a1 是 DTB PA。dtb_init 在高地址模式下通过启动直接映射读取它。

FDT 中多字节字段按大端解释；不能因为客户机通常小端，就把字节流直接当本机整数读。#address-cells/#size-cells 决定 reg 属性内地址和大小用了多少个 32 位单元，解释 memory 节点的 reg 要参考父节点的 cells。

当前 parser 检查 magic、总长度、结构/字符串块范围、token、节点层次、属性长度、保留表终止项和溢出，支持 1/2-cell 字段；可合并顺序相邻段，不支持通用不连续 RAM bank 管理。检查二进制格式合法不等于证明硬件地址一定可读，后者有平台前提。

**如果 OS 事先不知道可用物理内存范围？**

> 优先读启动协议提供的映射，例如 DTB、UEFI GetMemoryMap、传统 x86 E820，并排除固件和设备保留区。盲目读写未知地址可能碰到 MMIO 或总线错误，不是通用可靠方案。本实验实现了当前 QEMU 的 DTB 路径，未实现跨平台内存探测。

256 MiB 时打印探测到 256 MiB，却只管理 128 MiB，是显式 PHYSTOP 上限，不是 DTB 解析少了一半。当前分页映射更宽，允许访问上限外的 DTB，但不能据此分配那里的页。

## 11. 分页、Sv39、satp：C 必须讲清楚

### 11.1 为什么 4 KiB 页、512 项和三级

Sv39 的有效 VA 位为 39 位：

```text
高位 63:39：重复 bit38，必须规范符号扩展
VPN[2]：38:30，9 位
VPN[1]：29:21，9 位
VPN[0]：20:12，9 位
offset：11:0，12 位
```

一项 PTE 8 字节，一张表 4096/8=512 项，需要 9 位索引。三级提供 9*3+12=39 位地址表示；64 位寄存器不代表每个 64 位模式都是有效 Sv39 地址。规范低地址区和高地址区各 256 GiB，总表示范围为 512 GiB。

层级从根 level=2 到 level=0；QEMU 循环 i=0 指根层，两种编号不要混淆。level 2/1/0 叶子分别覆盖 1 GiB/2 MiB/4 KiB，需要相应物理对齐。非叶子 PPN 指向下一张页表，不是被访问的数据页。

### 11.2 satp 是什么，怎么解码

RV64 satp：MODE[63:60]、ASID[59:44]、PPN[43:0]。

```text
satp = (8ULL << 60) | (root_pa >> 12)
root_pa = (satp & ((1ULL<<44)-1)) << 12
```

MODE=0 是 Bare，MODE=8 是 Sv39。ASID 用于区分地址空间的翻译缓存上下文，本实验 ASID=0。根必须填 PA 的页号，不能把高地址 Page 指针或根 VA 原样填进去。

既有现场 satp=0x8000000000080207，解得 MODE=8、根 PA=0x80207000。`satp virtual address` 这条历史命名输出实际打印的是启动根页表 VA，不是“satp 寄存器本身有虚拟地址”。

### 11.3 PTE 各位与当前 0x200000cf

| 位 | 含义 | 本实验叶子 |
|---|---|---|
| 0 V | 有效 | 1 |
| 1 R | 可读 | 1 |
| 2 W | 可写 | 1 |
| 3 X | 可执行 | 1 |
| 4 U | 用户可访问 | 0 |
| 5 G | 全局映射 | 0 |
| 6 A | 已访问 | 1 |
| 7 D | 已写入 | 1 |
| 9:8 RSW | 软件保留 | 0 |
| 53:10 PPN | 物理页号 | 0x80000 |

普通有效非叶子项的 R/W/X 均为 0；有 R 或 X 的有效项可为叶子，还需检查权限、对齐及其他约束。W=1 且 R=0 是保留非法组合，不能作为有效的“只写页”。

本项目静态项 `(0x80000<<10)|0xcf` 的 PPN 是 0x80000，即物理基址 0x80000000。根项 2/511 都是 1 GiB 叶子，而非第二张表。

### 11.4 启动两条映射为何都需要

```text
根项 2：VA 0x80000000..0xbfffffff → 同址 PA
根项 511：VA 0xffffffffc0000000..0xffffffffffffffff
          → PA 0x80000000..0xbfffffff
```

低映射维持写 satp 后尚未跳高地址时的取指；高映射支持内核按高链接地址执行并使用高地址栈。写 satp 不会自动把 PC 加偏移，必须显式跳转。两段 VA 可以指向同一物理页，称为别名；本项目未撤销低映射。

根页表放 .data 并对齐到整页，内核尚未清 BSS 前就可读取。高地址栈初始化完成后才进入 C。BSS 由 kern_init 清零，不能先把 DTB 信息写入 BSS 全局变量再把它清掉，所以参数直接从 a0/a1 传进来。

## 12. TLB、sfence.vma、异常与实验边界

**TLB 是什么？**

> TLB 缓存最近的虚拟页到物理页翻译及权限，命中可跳过页表遍历。TLB miss 仅表示缓存里没有当前结果，不等于页面不存在，也不等于 page fault。

MMU 是完成地址翻译与访问权限检查的硬件逻辑；页表是内存中的数据；TLB 是翻译结果缓存。Cache 缓存指令/数据内容，与 TLB 的职责不同。

**改了 PTE 为何还要 sfence.vma？**CPU 可能仍用旧翻译。页表内存写入与翻译缓存失效是不同动作；在所需顺序下执行 sfence.vma，使后续地址翻译不再使用应失效的旧结果。它不是 flush 所有数据 cache，也不会归还物理页。写 satp 本身不能当作完整刷新保证。

当前 `sfence.vma` 无参数，作用于当前 hart 的相关翻译状态；多核还需通知其他 hart 并等待它们完成失效，本实验未实现 shootdown。ASID 与定址 fence 可以减少刷新范围，但本项目未实现进程地址空间切换。

**TLB miss、缺页和访问错误区别：**

- TLB miss：可能查表成功并回填，客户机不必看见异常。
- 页故障：可能因 V=0、权限、非规范 VA、大页对齐等翻译条件失败而产生。
- 物理访问错误：可能由 PMP 或底层物理内存访问失败等引起，不能统称缺页。

RISC-V 对真实硬件异常常查 scause/sepc/stval；A 的历史取指故障记录中 scause=12 表示 instruction page fault。S 模式 ecall 陷入 M 时 mcause=9，它与缺页不同；OpenSBI 处理后返回。当前内核使用旧式 SBI console 扩展 a7=1 输出字符，不等于实现了完整用户态系统调用框架。

本次 PTE 已预置 A/D=1，观察到了相关条件，但没有真正进入 A/D 更新分支；也未测试用户隔离、W^X、按需分页、换页或完整缺页处理。

## 13. 双 GDB 与 QEMU 源码：C 的主答题

### 13.1 为什么需要两个 GDB

> gdb-multiarch 通过 QEMU stub 调试 RISC-V 客户机，观察内核寄存器和指令；宿主原生 GDB 调试 x86-64 QEMU 进程，观察它如何用 C 代码模拟 MMU/TLB。宿主暂停时客户机调试器可能等待，是正常关系。

宿主 `$pc` 是 x86-64 PC，客户机 `$pc` 是 RISC-V PC；宿主的 env->satp 才是被模拟 CPU 的 satp。客户机 PA 也不是宿主指针，QEMU 还需要把客户机物理内存定位到宿主 RAM 后端。

调试版 QEMU 用 `--enable-debug` 编译，有源码调试信息；保存在缓存目录，不 make install 覆盖系统版。本次用上游 6.2.0，指导书的 4.1.1 函数/行号不能直接照搬。脚本以 QEMU 为宿主 GDB 的子进程，不依赖修改 ptrace 系统策略。

### 13.2 实际调用路径与条件断点

```text
取指：get_page_addr_code_hostp
  → 软件 TLB 检查，先主表/必要时 victim TLB
  → tlb_fill → riscv_cpu_tlb_fill → get_physical_address
  → 成功翻译及 PMP 检查 → tlb_set_page → 继续执行

写数据：客户机 sb → TCG 生成代码 → full_stb_mmu/store_helper
  → tlb_fill → riscv_cpu_tlb_fill → get_physical_address
```

TCG 是 QEMU 的动态翻译执行机制，生成的快路径可能直接访问软件 TLB，不是每次访存都逐个进入这些 C 函数。TB 是已翻译指令块，TLB 是地址翻译缓存，两者不是同一种缓存。

条件断点选 `addr==目标VA && !is_debug`，避免每次固件访问都停下；`!is_debug` 排除 GDB 自己读内存/反汇编引发的地址查询。实际写入还可限制 access_type=MMU_DATA_STORE。

### 13.3 把一条 VA→PA 现场完整讲出来

以实际 kern_init 取指为例：

```text
VA = 0xffffffffc0200032
satp = 0x8000000000080207 → root_pa = 0x80207000
idx = (VA >> 30) & 511 = 511
pte_pa = 0x80207000 + 511*8 = 0x80207ff8
PTE = 0x200000cf，PPN = PTE >> 10 = 0x80000
命中根层 1 GiB 叶子
PA = 0x80000000 | (VA & 0x3fffffff) = 0x80200032
```

一般大页的合成形式：

```text
vpn = VA >> 12
PA = ((PPN | (vpn & ((1<<ptshift)-1))) << 12) | (VA & 0xfff)
根层 ptshift=18，中间层=9，末层=0
```

根层大页的低两级 VPN 是大页内偏移的一部分，不能只拼 12 位 offset。QEMU 虽配置 levels=3，但本次 i=0 就命中叶子，实际只读了一层页表。理论多级循环与本次现场必须分开说。

真实写指令是 memset 中的 `sb a1,-1(a5)`。第一次循环 a5 先加一，因此写 VA=edata=0xffffffffc0208010；宿主看到 size=1、MMU_DATA_STORE、is_debug=false，最终 PA=0x80208010。这样既有取指，也有实际写内存的现场。

### 13.4 如何证明 TLB miss/fill/hit

取指 C 检查在 QEMU 6.2.0 的 `accel/tcg/cputlb.c:1506`。首次 entry->addr_code 为无效标记，与 VA 页不匹配；随后 get_physical_address 查表，tlb_set_page 接收 VA 页 0xffffffffc0200000、PA 页 0x80200000、prot=7、size=4096。

后续同页访问，entry->addr_code 已为 0xffffffffc0200000。源码 next 从 1506 直接到 1523，跳过 miss 分支，这才是直接观察命中的证据，而不只是“后来没触发查表断点”。

prot=7 是 QEMU 的读/写/执行权限表示，不是 PTE 的 0xcf。客户机叶子为 1 GiB，本次 QEMU 回填粒度为 4 KiB，也不能混为同一数字。

### 13.5 Bare 为何仍然看到 QEMU 软件 TLB

> Bare 的架构语义是不做分页翻译。QEMU 的软件 TLB 除缓存翻译和权限，还加速客户机访问到宿主 RAM 的定位，所以 Bare 下可以仍走软件 TLB；未命中后 MODE=Bare 直接返回 PA=VA，没有读取页表。

本次选 S 模式内核物理入口 0x80200000，satp=0、mmu_idx=1，确实观察 MODE=Bare 分支；没有用 M 模式快捷路径冒充这个对比。真实 CPU 内部是否以某种结构缓存 Bare 访问由实现决定，不能拿 QEMU 软件 TLB 推断所有硬件电路。

### 13.6 指导书的六类调试追问对应答案

| 类别 | 回答要点 |
|---|---|
| 关键调用路径及分支 | 取指/写入两条路径，主/victim TLB、Bare/Sv39、非叶子/叶子、权限/PMP、回填 |
| 单步翻译 | root PPN→索引→PTE PA→PTE→权限与对齐→PA；本次一级大页提前返回 |

## 14. 测试为什么可信：不只会说“全部 PASS”

| 检查 | 数量或内容 | 为什么能检出错误 |
|---|---|---|
| 正常容量/后端 | 3 后端 × 64/128/256 MiB = 9 次 | 防止固定容量、后端没切换或管理上界错误 |
| 非法调用 | 8 个公共场景 × 3 后端，Buddy 另 2 个，共 26 次 | 检查指定所有权/边界拒绝，不能任意 panic 都算成功 |
| 随机页分配 | 每个正常场景 1200 步 | 独立位图、数据标签和逐步计数发现重叠、数据破坏及记账错误 |
| Fit 策略区别 | 隔离 8 页和 4 页的候选 | 真正区分 First-Fit/Best-Fit，不能只改名字 |
| Buddy 拆合 | 隔离 8 页并耗尽其他可用页 | 排除其他空闲块掩盖拆分/合并缺陷 |
| SLUB | 规格边界、600 对象、重用、OOM | 写满请求内容并核对其他对象，检查隔离与回收 |
| 启动 GDB | 3 后端 × 3 容量 = 9 次 | 验证 satp、高地址、PTE、BSS、SBI 和 PMM 布局 |
| QEMU 源码 | Bare/Sv39、取指/写入、缓存状态 | 用真实调用栈与源码单步确认 MMU 路径 |

35 个功能场景=9 个正常+26 个指定拒绝。9 个启动检查是额外的，不要把它们说成 35 个里又重复计算的 9 次启动步骤；它们是独立的 GDB 运行。

**为什么计数恢复还不够？**两个错误可能互相抵消，或者分配区间重叠但计数仍对。还需检查独立占用位图、数据标签、实际地址、块对齐和选择策略。

**预期失败怎样判？**先出现对应 EXPECT 标记，再命中指定断言；未知 panic、超时或没有结果算失败。当前 runner 的负例针对受测调用序列，不代表已经证明能拒绝所有非法程序。

**测试能证明什么？**只能说明给定实现、环境及场景通过。没有课程原测试、并发、多 bank、通用动态映射或形式化证明，不可外推“绝对正确”。

接下来是 **GDB 命令**，不要直接输在 Bash：

```gdb
thbreak *0x80200000
continue
info registers pc a0 a1 satp
thbreak kern_init
continue
info registers pc sp satp
x/gx ((unsigned long)&boot_page_table_sv39)+2*8
x/gx ((unsigned long)&boot_page_table_sv39)+511*8
thbreak run_selftests
continue
p pmm_manager->name
p nbase
p npage
p npage-nbase
p/x pages
p/x free_begin
p/x managed_end
ptype /o struct Page
```

解释：物理入口 satp=0；高 C 入口 MODE=8；两个根项为 0x200000cf；自测入口 PMM 已初始化，所以可以解释 Page 数组和空闲区。

此时还可直接用 GDB 算式验证地址换算，无需调用或修改内核分配器：

```gdb
p/x ((unsigned long)(1024+nbase)*4096)
p/x ((unsigned long)(1024+nbase)*4096+va_pa_offset)
p/x ((unsigned long)&pages[1024].page_link-(unsigned long)&pages[1024])
```

依次应为 PA=0x80400000、KVA=0xffffffffc0400000、成员偏移=0x18。这些表达式只做读值/计算，避免在 GDB 中不熟练地调用 alloc/free 改变自测初始状态。

结束时 GDB 中输入 detach、quit，再回 QEMU 窗口退出。thbreak 是临时硬件断点；b 是普通断点；si 是一条客户机指令；next/step 是源码级动作，遇到优化代码可能一行对应多条指令或变量不可见。

## 17. 高频快问快答：能在 20 秒内说清

| 问题 | 简短答案 |
|---|---|
| page_init 干什么？ | 根据 RAM 范围建立 Page 数组，排除保留区域，登记可分配整页 |
| pmm_init 和 page_init 有何区别？ | 前者选择/初始化管理器并组织流程，后者建立布局和可用页状态 |
| npage 是页数吗？ | 本项目是 PFN 排他上界，页数=npage-nbase |
| pages 指向页数据吗？ | 指向 Page 元数据数组；页内容用 page2kva |
| Page+1 为什么对应下一物理页？ | 数组按 PFN 连续组织，每个元素代表一个 4 KiB 帧 |
| page2pa 公式？ | (page-pages+nbase)*4096，前提是合法描述符 |
| pa2page 公式？ | pages+(pa/4096-nbase)，得到所在帧的描述符 |
| va_pa_offset 是谁减谁？ | 高直接映射 VA-PA |
| 链表空时 next 指哪？ | 指回哨兵自身，prev 也相同 |
| page_link 指针怎样还原 Page？ | 转字节指针后减 offsetof(Page,page_link) |
| property 是引用数吗？ | 不是；Fit 块头页数，Buddy 块头阶，ref 才是引用字段 |
| 每个空闲页都挂链吗？ | Fit 通常只挂每个空闲块的头 |
| 空闲 10 页，申请 6 页为何失败？ | 总量够但没有足够大的连续块 |
| First/Best-Fit 差别？ | 第一个能放下，对比最小能放下 |
| 相邻链表项一定合并吗？ | 不一定，还要物理页区间连续 |
| 合并改变 nr_free 吗？ | 本次释放增加计数；合并本身不再增加 |
| Buddy 申请 5 页占多少？ | 8 页，按原请求 5 归还 |
| Buddy 相邻块一定能合并吗？ | 必须同阶、空闲、边界合法且 XOR 伙伴 |
| SLUB 为什么要规格？ | 页内高效复用小对象空间，减少每个小对象独占整页的浪费 |
| MMU、PTE、TLB 区别？ | 翻译执行逻辑、内存中的映射数据、翻译缓存 |
| TLB miss 就缺页吗？ | 不，查表可能成功并回填 |
| 写 satp 自动跳高地址吗？ | 不，PC 需显式转移，切换窗口需有效映射 |
| sfence.vma 会清物理内存吗？ | 不，它处理翻译相关同步/失效 |
| Sv39 每次查三层吗？ | 最多三层，本实验根层大页一次就返回 |
| 0xcf 和 prot=7 相同吗？ | 含义相关但编码不同，一个是 PTE 标志，一个是 QEMU 权限 |
| 256 MiB 为何只管 128 MiB？ | 实现设置 PHYSTOP 上限，并明确打印截断 |
| alloc_page 会自动建新映射吗？ | 不，本实验访问它靠既有内核直接映射 |
| 源码调试和内核调试为何分两个？ | 宿主 ISA/对象与客户机 ISA/对象不同 |
| 35+9 都通过能说官方满分吗？ | 不能，原始课程测试缺失，结果是自建验证 |
| 动态 map/unmap/query 做了吗？ | 当前未交付；只做启动映射和只读检查 |

## 18. 原理扩展：知道意义，明确未实现

- **内部/外部碎片**：分配块内部的未用空间，对比空闲空间分散无法满足连续请求；Buddy/规格对象都有内部碎片，Fit 可能有外部碎片。
- **多级页表**：通过按需分配表页节省稀疏空间开销；大页减少表项和翻译层数，代价是粗粒度权限及可能的浪费。
- **按需分页/换页**：把虚拟页的驻留与访问关联，依靠缺页处理调入或分配；本实验没有该完整机制。
- **用户隔离**：依靠不同根表和 U/R/W/X 等权限限制访问；本实验是共享的宽松启动内核映射。
- **COW**：共享只读页、写故障时复制，需要引用计数、权限修改和缺页处理；本项目仅有 ref 字段不等于实现 COW。
- **并发和 NUMA**：多 hart 修改空闲链表需锁或其他同步，页表更新需跨核失效；NUMA 还涉及内存访问距离和分配策略，本实验未实现。
- **权限与所有权不同**：PTE 可写不等于允许把页交给某个分配请求，PMM 状态合法也不等于当前 VA 映射权限正确。
