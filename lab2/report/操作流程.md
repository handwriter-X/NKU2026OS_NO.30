## 2. 编译并普通启动内核

在 **Ubuntu** 中执行：

```bash
make -j2
make qemu
```

默认使用 Best-Fit。编译产物为：

| 文件 | 用途 |
|---|---|
| `bin/best_fit/0/kernel` | 带调试符号的 ELF，供 GDB 使用 |
| `bin/best_fit/0/ucore.img` | QEMU 启动的内核镜像 |
| `obj/best_fit/0/` | 当前配置的中间产物 |

启动后重点观察：

```text
OpenSBI v0.9
(THU.CST) os is loading ...
DTB: ... size=128 MiB
memory management: best_fit_pmm_manager (Sv39 integrated)
FREE: ... pages=31727
satp virtual address: 0xffffffffc0207000
satp physical address: 0x0000000080207000
...
LAB2 B SELFTESTS PASSED: best_fit_pmm_manager
```

这些输出依次说明：OpenSBI 交出控制权，内核进入分页模式，从 DTB 取得 RAM 范围，排除固件、内核与描述符占用后登记空闲页，最后完成分配器和对象分配测试。

**最后停止输出是正常的：内核进入空循环。**退出 QEMU：按 **Ctrl+A，松开后按 X**。

实际初始化顺序是：

```text
复位 ROM → OpenSBI → 物理 kern_entry
→ 设置 satp、sfence.vma → 高地址栈与 kern_init
→ 清 BSS → DTB → pmm_init → page_init
→ 分配器与 SLUB 自测 → 空循环
```

### 2.1 扩展任务与思考题的演示顺序

| 演示项目 | Ubuntu 中的操作 | 重点展示 |
|---|---|---|
| Buddy | `make PMM=buddy grade` | 分阶、拆分与合并，请求 5 页实际占 8 页 |
| 简化 SLUB | `make PMM=best_fit grade` | SLUB 自测通过；小对象分配、复用、空 slab 归还 |
| 思考题：不知道内存范围怎么办 | 依次运行下面三种容量 | DTB 识别值随容量变化，区分发现范围与管理范围 |
| QEMU 页表/TLB 源码 | `make grade-source`，详细步骤见后文 | Bare/Sv39、查表与 TLB miss/fill/hit |

**思考题也要现场演示。**在 Ubuntu 的 `lab2/code` 中依次执行，每次运行结束后按 **Ctrl+A，松开后按 X** 退出 QEMU，再执行下一条：

```bash
make PMM=best_fit MEMORY=64M qemu
make PMM=best_fit MEMORY=128M qemu
make PMM=best_fit MEMORY=256M qemu
```

观察 `DTB`、`MANAGED`、`FREE` 三行：

| 输入容量 | DTB 识别的 RAM | 实际管理范围 |
|---|---|---|
| 64M | [0x80000000, 0x84000000)，64 MiB | 64 MiB |
| 128M | [0x80000000, 0x88000000)，128 MiB | 128 MiB |
| 256M | [0x80000000, 0x90000000)，256 MiB | 128 MiB，输出 capped 提示 |

讲解顺序：**启动时 a1 提供 DTB 地址 → [dtb.c](../code/kern/driver/dtb.c) 解析 memory 节点的 reg → [pmm.c 的 page_init](../code/kern/mm/pmm.c) 取实际 RAM 终点与 PHYSTOP 的较小值 → 扣除固件、内核、描述符等占用，得到 FREE。**因此 FREE 小于管理总量；256M 识别成功而只管理 128 MiB，是当前管理上限导致的。

现场结论：本平台通过启动信息获取 RAM 范围；其他平台可使用 UEFI GetMemoryMap、x86 E820。未知地址可能对应 MMIO 或不可访问区域，不能靠随意写读可靠地探测。本演示覆盖当前 QEMU 连续 RAM 的发现和管理边界，尚未实现跨硬件通用探测及任意保留区的完整扣除。问题对应的知识结构和讲解词见 [答辩速记.md 第六组](答辩速记.md#第六组扩展任务做了什么怎样展示)。

## 4. 手动内核 GDB：观察分页前后

准备两个 Ubuntu 终端，均进入 `lab2/code`。可以在两个 PowerShell 窗口分别运行第 1 节的 WSL 进入命令。

### 4.1 终端一：启动暂停的 QEMU

```bash
make debug
```

它启动 QEMU 并暂停 CPU，使用 GDB 端口 1234。此时没有正常启动输出是预期行为。

### 4.2 终端二：连接 GDB 并观察物理入口

```bash
make gdb
```

进入 `(gdb)` 后执行：

```gdb
thbreak *0x80200000
continue
info registers pc a0 a1 satp
```

本次实测：

```text
pc    = 0x80200000
a0    = 0
a1    = 0x87000000
satp  = 0
```

这里是内核的物理入口：a0 为 hart ID，a1 为 DTB 物理地址，satp=0 表示 Bare。DTB 的位置由 QEMU/容量决定，不应硬编码。

注意先停在物理 `0x80200000`，不要把 kern_entry 的高链接地址当成分页前实际执行地址，否则可能一直等不到断点。

### 4.3 观察高地址 C 入口与启动页表

继续在 **GDB** 中执行：

```gdb
thbreak kern_init
continue
info registers pc sp satp
```

本次实测：

```text
pc    = 0xffffffffc0200032
sp    = 0xffffffffc0207000
satp  = 0x8000000000080207
```

这说明已经切换到高地址 C 入口和栈。satp 最高四位为 8，表示 Sv39；根 PPN 为 0x80207，根页表 PA 为 0x80207000。

查看根项 2 和 511：

```gdb
x/gx ((unsigned long)&boot_page_table_sv39)+2*8
x/gx ((unsigned long)&boot_page_table_sv39)+511*8
```

两项应都是：

```text
0x00000000200000cf
```

项 2 提供低地址恒等映射，使写 satp 后到跳高地址前的取指有效；项 511 提供内核高地址映射。0xcf 表示 V/R/W/X/A/D，U=0。根项已含 R/W/X，因此是 1 GiB 叶子，而非下一级表指针。

### 4.4 观察 PMM 初始化结果并退出

继续执行：

```gdb
thbreak run_selftests
continue
p pmm_manager->name
p/x free_begin
p/x managed_end
p npage-nbase
```

本次输出：

```text
"best_fit_pmm_manager"
0x80411000
0x88000000
32768
```

这里 PMM 已初始化，但自测尚未开始。32768 是描述符覆盖的总物理页数，包含保留页；可分配页数还要扣除固件、内核和描述符占用，不能把二者混同。

退出 GDB：

```gdb
detach
quit
```

detach 后客户机继续运行。回到终端一，按 **Ctrl+A，松开后按 X** 结束 QEMU。

## 5. QEMU 源码双 GDB：观察 MMU 与 TLB

上一步调试客户机内核，这一步再用宿主 GDB 调试 QEMU 本身。

| 工具 | 调试对象 | 观察内容 |
|---|---|---|
| gdb-multiarch | RISC-V 内核 | 客户机指令、pc、satp 和访存地址 |
| 原生 gdb | x86-64 QEMU 进程 | 软件 TLB 查询、页表遍历和 PA 合成 |

### 5.1 本机运行入口

本机已经构建调试版 QEMU，在 **Ubuntu** 中直接运行：

```bash
make grade-source
```

脚本自动协调两套 GDB：客户机停到目标位置，宿主按目标地址设置条件断点，再逐条执行 QEMU C 源码。宿主暂停时客户机 GDB 可能等待，这是两层调试的正常关系。

成功标志为：

```text
PASS: Bare/Sv39 source stepping, PTE, TLB miss/fill/hit, dual GDB and kernel selftests
```

调试版默认路径为 `$HOME/.cache/oslab/qemu-6.2.0/build-debug/qemu-system-riscv64`。脚本针对上游 QEMU 6.2.0 的源码行号，不能随意换成其他版本。

### 5.2 新环境首次构建调试版 QEMU

仅在工具缺失或调试版尚未构建时执行。本节为 **Ubuntu** 命令：

### 5.3 按顺序阅读实际调试现场

在 **Ubuntu** 中执行：

```bash
less evidence/qemu-mmu/host-gdb.log
```

在 less 中按 `/` 后输入关键词搜索，按 n 找下一个匹配，按 q 退出。建议依次搜索：

```text
Bare software TLB
Sv39 single-step
subsequent fetch
First BSS store
```

分别观察以下四件事：

1. **Bare**：satp=0，翻译直接返回 PA=VA，没有读取页表；QEMU 仍使用软件 TLB 加速访问。
2. **Sv39**：TLB 未命中，进入 `riscv_cpu_tlb_fill` 和 `get_physical_address`，读取根表及 PTE，合成 PA。
3. **后续访问**：缓存页标记匹配，单步跳过 miss 分支，实际观察到 TLB 命中。
4. **实际写入**：跟踪 memset 的 `sb a1,-1(a5)`，验证数据写地址也按页表翻译。

本次实际取指翻译为：

```text
VA        = 0xffffffffc0200032
根表 PA   = 0x80207000
根表索引  = 511
PTE 地址  = 0x80207000 + 511*8 = 0x80207ff8
PTE       = 0x200000cf
最终 PA   = 0x80200032
```

Sv39 最多走三级，但本次根项已经是 1 GiB 大页叶子，第一次循环就返回。不能描述为实际走满了三层。

BSS 首次写入实测为 VA `0xffffffffc0208010` → PA `0x80208010`，`access_type=MMU_DATA_STORE`、`is_debug=false`，调用栈包含 store_helper。`is_debug=false` 用于排除调试器自己读内存引发的翻译查询。

另外两份日志分别是：

```bash
less evidence/qemu-mmu/guest-gdb.log
less evidence/qemu-mmu/qemu.log
```

第一份看客户机断点、寄存器和访存指令；第二份看调试结束后内核是否仍完整通过自测。更详细的 C 调用路径、分支分析和截图见 [gdb-mmu.md](gdb-mmu.md)。
