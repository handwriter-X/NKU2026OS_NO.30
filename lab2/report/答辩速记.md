# Lab2：顺着执行过程理解整套流程

这次实验要把一段原始 RAM，逐步变成内核能够申请、访问和归还的内存。下面按真实执行顺序展开：**启动 → 建立映射 → 读取硬件信息 → 划定可用页 → 组织空闲结构 → 申请 → 访问 → 回收 → 验证。**每一步都说明它接到什么、具体改变什么、把结果交给谁；概念随流程出现。

1. **机器启动，固件把执行权和硬件信息交给内核。**

   编译、链接先把源代码变成内核镜像。链接脚本决定函数和变量使用什么地址；QEMU 则把镜像放到模拟 RAM 中。程序中的符号地址与镜像实际所在位置，之后要靠页表联系起来。

   QEMU 启动模拟机器后，先执行复位代码和 OpenSBI。OpenSBI 是固件，负责准备启动环境，再跳到内核的汇编入口 `kern_entry`。所以它不是在调用某个内存分配函数，而是把整个处理器的执行权交给内核。

   交接时还提供当前 hart 信息和 DTB 的位置。DTB 是一份硬件描述，其中包含 RAM 范围；现在先保留这个入口参数，等内核具备 C 运行环境后再读取。当前 entry.S 不覆盖这些参数寄存器，后面可以直接把它们传给 `kern_init`。

   **此时的状态是：内核指令已经开始执行，但分页尚未开启，内核自己的栈和动态内存管理还没有准备好。**因此下一步不能直接进入复杂的内存分配，而要先建立后续运行所需的地址环境。

   对应文件：[kernel.ld](../code/tools/kernel.ld)、[entry.S 的 kern_entry](../code/kern/init/entry.S)。

2. **准备启动页表，先说明程序地址应当对应哪段物理内存。**

   CPU 最终要访问的是实际物理内存，程序里的指针却使用虚拟地址。页表记录虚拟地址与物理地址之间的对应关系。这里的“建立映射”不是复制内核，也不是把内存搬到高处，而是让另一套地址能够指向原来那段物理内存。

   这时页分配器尚未初始化，所以不能依靠 alloc_pages 来申请最初的页表。当前实现把 `boot_page_table_sv39` 预先放进内核数据段，镜像装载时它就已经存在。因此，**启动页表先提供基本访问能力，后续动态分配器才能在这个环境中建立起来。**

   页表里同时安排低地址恒等映射和高地址直接映射。低地址映射让当前正在执行的启动代码在切换后仍能被访问；高地址映射让内核后续使用的符号地址能找到相同的物理内容。两种地址可以暂时指向同一段 RAM。

   页表项需要表达两件事：目标物理位置在哪里，以及允许什么访问。当前启动用大页叶子直接覆盖一段地址，不必为这段映射继续建立下级表。“有多级页表机制”不意味着每次都必须查到最末层。

   **此时表已经准备好了，但 CPU 还没有被通知使用它。**下一步才真正切换地址翻译方式。

   对应代码：entry.S 中的 `boot_page_table_sv39` 及相关静态表项。

3. **让 CPU 使用页表，再切换到内核栈和 C 入口。**

   `kern_entry` 先取得启动根表的物理位置，转换成根表物理页号，再把它和分页模式一起写进 satp。satp 是告诉 CPU“采用什么翻译方式、从哪张根表开始查”的寄存器。这里必须提供物理位置，因为查表本身不能先依赖一个尚未解释的虚拟地址。

   写入 satp 后，后续取指和访存开始遵循分页规则，但 PC 不会自动跳到高地址。当前指令仍在原来的低地址位置，所以先前保留的恒等映射必须继续有效，否则可能刚开分页就无法取到下一条指令。

   随后执行 `sfence.vma`，同步当前 hart 的地址翻译状态。它针对页表相关的翻译，不是清空普通数据缓存，也不是自动通知其他处理器。接着设置 sp，让它指向内核自己的启动栈，再跳转到高地址的 `kern_init`。

   栈用于保存函数调用中的局部变量、返回信息等，进入普通 C 函数前需要有可用的栈。**完成后，内核已经能用自己的虚拟地址和栈运行 C 代码；物理页分配器仍然尚未建立。**

   对应代码：entry.S 中写 satp、执行 sfence.vma、设置 sp、跳转 kern_init 的连续指令。

4. **C 入口清理初始状态，再按顺序启动各项功能。**

   `kern_init` 先清零 BSS。BSS 中包含应当以零状态开始的全局变量；如果先把 DTB 解析结果或 PMM 状态写进去，再清零，就会把刚建立的信息抹掉。所以清零必须先于这些初始化。

   清理完后打印启动信息，然后依次执行 `dtb_init → pmm_init → run_selftests`。dtb_init 提供机器的 RAM 信息，pmm_init 依据这些信息建立管理能力，run_selftests 才能申请和归还内存。

   这个调用顺序本身就说明了数据依赖：分配器不能先于内存范围初始化，功能测试也不能在分配器尚未准备好时申请页面。当前自测之后进入空循环，没有继续启动进程调度或用户程序。

   **接下来传给 DTB 初始化的是固件提供的位置参数；DTB 初始化产生的结果，又会成为 PMM 初始化的输入。**

   对应文件：[init.c 的 kern_init](../code/kern/init/init.c)。

5. **解析 DTB，把启动信息变成内核可查询的 RAM 范围。**

   `dtb_init` 接收 DTB 的物理地址，通过启动直接映射得到能读取它的虚拟地址，再交给 `dtb_parse`。解析器先验证格式标记、总长度和各区块边界，防止把不完整数据或任意内存误当作设备树。

   接着遍历节点和属性，识别描述内存的节点，从 reg 属性取得起点和长度。地址和长度如何拼接，要依据父节点对字段格式的声明，并处理设备树数据的字节序。它是在解读启动方提供的描述，不是靠向未知地址写入来试探 RAM。

   得到结果后保存到内部状态，后面 `get_memory_base` 与 `get_memory_size` 可以取出。无效信息应当终止初始化，不能随便假设一段默认 RAM 后继续，否则可能把设备地址或不存在的区域交给分配器。

   这里分清三个层次：DTB 说机器实际有哪些 RAM；管理上限决定本内核打算管理其中多少；扣掉固件、内核和管理数据后，剩下的才可分配。**发现了 RAM，不等于这些 RAM 已经全部空闲。**

   当前实现面向连续 RAM，也没有完整处理任意硬件保留区。接下来 PMM 会在这一平台约定下，进一步划定管理与空闲边界。

   对应文件：[dtb.c 的 dtb_init、dtb_parse 和查询接口](../code/kern/driver/dtb.c)。

6. **选择物理页管理器，先建立空容器，再规划实际资源。**

   `pmm_init` 根据构建选项，把 pmm_manager 指向 First-Fit、Best-Fit 或 Buddy 的注册结构，当前默认 Best-Fit。这个结构保存各项操作的函数指针，相当于规定统一的调用入口：上层说“申请连续页”，具体怎样找由当前管理器决定。

   例如上层调用 `alloc_pages`，公共接口再调用 `pmm_manager->alloc_pages`；换算法就是改变这些指针实际指向的实现，不是仅改输出名称。当前 Best-Fit 的注册函数最终复用 Fit 公共实现，并选择 Best-Fit 策略。

   选定管理器后，先调用 `pmm_manager->init`。Fit 把空闲链表初始化为空、空闲计数清零；Buddy 则准备各个阶的空链表。此时没有任何页登记进去，尚不能期待申请成功。

   随后 pmm_init 调用 `page_init`。**管理器现在解决了“由谁管理”，page_init 接下来解决“究竟有哪些资源可以交给它”。**这两件事必须先后完成。

   对应文件：[pmm.c 的 pmm_init、alloc_pages](../code/kern/mm/pmm.c)、[pmm.h 的 pmm_manager](../code/kern/mm/pmm.h)、[best_fit_pmm.c 的注册结构](../code/kern/mm/best_fit_pmm.c)。

7. **建立 Page 数组，划出真正可以分配的完整页面。**

   `page_init` 取出 DTB 中的 RAM 起点与长度，检查范围和计算是否有效，再结合 PHYSTOP 管理上限得到 managed_end。RAM 超出当前能力的部分不进入分配器；末尾不满一个完整页的部分也排除。

   接着为受管 RAM 的每个物理页建立一个 Page 描述符。物理页用来存实际内容，Page 用来记录状态；描述符数组自身也占 RAM，不能把它当成不花空间的抽象表。数组放在内核末尾之后，所以最终布局是：**固件保留区 → 内核 → Page 数组 → 空闲页。**中间还可能有对齐空隙。

   `pages` 指向描述符数组；`nbase` 表示数组第一个元素对应的绝对物理页号；`npage` 是管理页号的上界。描述符数量来自两者之间的范围。这样数组里的每一项，都能对应到一个实际物理页，包括那些属于固件或内核的保留页。

   内核末尾符号 end 使用虚拟地址，而 RAM 边界是物理地址，因此必须先统一地址含义，才能计算描述符占用了多少空间。描述符末尾向上按页对齐得到 free_begin，保证下一空闲页不碰到已占用字节；管理末尾向下对齐，保证不越过有效 RAM。

   数组建立后先将所有描述符标为 Reserved，并初始化节点。这样在可用区尚未登记时，任何页面都不会被误认为可以申请。只有后面确认的空闲范围才清除保留状态。**有描述符，只代表这页被记录，不代表它可分配。**

   最后，page_init 把 free_begin 转为对应的 Page 指针，计算完整空闲页数量，交给 `pmm_manager->init_memmap`。空闲区为空时不登记；描述符本身放不下等布局错误必须被拒绝。

   对应代码：pmm.c 的 `page_init、pa2page`，以及 [memlayout.h 的 Page](../code/kern/mm/memlayout.h)。

8. **把空闲页组织成可查找的块，完成从 RAM 到分配器的交接。**

   对 Fit，`fit_init_memmap(base,n)` 接到的是一段已经确认可用的页面描述符。它验证范围和原有保留状态，清除这些页的保留标记，再调用 insert_block，把这一段组织为空闲块，最后增加空闲页计数。

   连续空闲页不必每页都挂链，只让块头进入按地址排序的双向循环链表。块头 property 记录该块有多少页，PageProperty 标志说明它确实是空闲块头。块内部的页依然有描述符，但没有独立块头身份，所以不能仅凭 property 是否为空判断整页状态。

   Page 中的 flags 记录保留、分配和块头等状态；alloc_span 与 requested 在已分配块头记录实际跨度和原始请求；ref 保留引用计数用途，当前并未实现完整映射引用管理。管理器的 nr_free 统计空闲页总量，不是链表节点数。

   链表操作通过 Page 内嵌的 page_link 进行。prev、next 指向前后节点，链表代码本身不知道 Page 的其他字段。遍历拿到节点后，`le2page → to_struct` 根据成员在结构体内的偏移，反推出 Page 的起始位置。

   头节点是哨兵，空表时前后指针都指回自身；它不代表物理页，不能当作 Page。只有真实空闲块节点才能用于恢复描述符。地址排序则为后面的前后合并提供邻接候选。

   如果选择 Buddy，同一登记接口会改为按大小和物理页号对齐拆分可用区，放入各阶链表。**登记完成后，管理器才真正拥有可分配资源；pmm_init 会核对空闲数量，再返回 kern_init。**

   对应文件：[default_pmm.c 的 fit_init_memmap、insert_block](../code/kern/mm/default_pmm.c)、[list.h](../code/libs/list.h)、[defs.h 的 to_struct](../code/libs/defs.h)、[buddy_pmm.c 的 buddy_init_memmap](../code/kern/mm/buddy_pmm.c)。

9. **进入自测并发起请求，沿调用链完成一次实际分配。**

   初始化返回后，kern_init 执行 run_selftests。当前是测试代码主动模拟内核使用者：需要连续物理页就调用 alloc_pages，需要一个按字节使用的对象就调用 kmalloc。先沿着整页申请看下去。

   `alloc_pages` 检查请求非空，然后调用当前管理器的分配函数。Fit 先看空闲总量是否足够，再遍历空闲块：First-Fit 遇到第一个能容纳请求的块就停止；Best-Fit 继续比较候选，保留最小的合适块，遇到精确匹配就可停止。

   选中后保存原块长度并摘掉原节点。如果请求只占它前面一部分，剩余部分会以新的块头重新插回空闲结构；如果刚好用完，就没有余块。随后 `pmm_mark_allocated` 检查页面状态，将请求范围标为已分配，清理旧的空闲块信息，在头部记录分配跨度和请求，最后减少空闲计数。

   这里实际变化的是描述符、链表和计数，没有把这段数据搬到别处。返回的 Page 指针代表“这一段物理页现在已经分给调用者”。如果找不到合适块，返回 NULL，不能改变空闲状态。

   总空闲数足够仍可能失败，因为当前接口要连续物理页，而空闲页可能散成互不相连的块，这就是外部碎片。Best-Fit 只保证这次选择最小合适块，留下的小余块是否有利，要看后续请求。若改进搜索速度，可以考虑大小索引或分桶，但拆分合并时也必须维护相应索引。

   若当前管理器是 Buddy，请求则先向上取整为合适阶，找不到就拆开更大的块，把不用的一半放回对应阶。最终记录原始请求和实际跨度，空闲计数扣掉实际占用；多于请求的部分是内部碎片。**Buddy 与 Fit 是同一调用位置的替代实现，不是先执行 Fit 再执行 Buddy。**

   对应代码：pmm.c 的 `alloc_pages、pmm_mark_allocated`，default_pmm.c 的 `fit_alloc_pages`，buddy_pmm.c 的 `buddy_alloc`。

10. **如果上层要的是对象，就在已分配页内继续分出可用空间。**

    请求来自 `kmalloc` 时，它先选择足以容纳请求的对象规格，在该规格的 slab 页中寻找空闲槽。已有空闲槽就直接复用，不需要每次都申请新页；只有没有空间时，才进入刚才讲过的页申请过程。

    新页返回的是 Page。SLUB 先通过 page2kva 得到页内容地址，在页首建立管理信息，记录对象规格、槽位数量、已用数量、空闲对象链和占用位图。然后把其余空间切成槽位，将空闲槽串起来，并将这一页登记到对应规格的缓存链。

    取对象时，从空闲对象链摘出一个槽，设置位图中的占用状态，增加已用数量，再返回槽位地址。空闲对象自己的内容可以暂存下一个空闲对象指针；对象交给调用者后，其用户内容由调用者使用。位图用于区分同一页内哪些槽已经被占用。

    较大对象不适合塞进这些固定规格时，就申请一段能放下对象和头部信息的连续页，在头部保留归还时需要的信息，再返回用户数据部分。若底层采用 Buddy，物理跨度还可能比请求页数更大。

    **此时整页申请返回描述符，小对象申请返回用户数据指针；SLUB 靠底层页面资源提供更细粒度服务。**当前是简化实现，空 slab 会直接归还，没有完整 Linux SLUB 的处理器本地缓存等机制。

    对应文件：[slub.c 的 kmalloc、slab 结构与缓存链](../code/kern/mm/slub.c)。

11. **通过正确的数据地址访问内容，由分页机制完成实际翻译。**

    直接拿到 Page 的调用者，要先用 page2pa 找到对应物理页，再用 page2kva 获得可访问页内容的内核虚拟地址。换算依据是描述符在数组中的位置、起始物理页号和高直接映射。Page 指针指向管理记录，不能当作那页的数据指针。

    这些换算不等于重新建页表。启动映射已经覆盖当前使用范围，所以申请只改变页面归属；CPU 访问内容时仍按页表翻译。TLB 命中就利用缓存，未命中则依据 satp 找根表，逐层读表项；非叶子继续下一级，合法叶子给出物理地址与权限，翻译成功后再回填缓存。

    若表项无效、权限不允许或地址不合法，则不能正常完成访问；这与“TLB 里暂时没有缓存”不同。当前启动采用大页叶子，可以提前完成翻译。这里分工明确：**分配器决定资源归属，页表决定地址对应，TLB 减少重复查表。**

    对应接口在 pmm.c 与 pmm.h，启动映射在 entry.S。访问完成后，下面沿资源归还的方向继续。

12. **先归还对象，判断是否需要把整页还给底层。**

    对象用完后调用 kfree。它将对象指针转换为物理位置，找到所属页和页头，检查该页是否由 SLUB 管理，再根据对象相对页头的位置算出槽位，验证边界、对齐和占用位。没有大小参数也能回收，正是因为这些信息保存在页头中。

    小对象归还后清除位图占用、减少已用数量，并把槽放回空闲对象链。只要还有对象存活，该页就继续由 SLUB 持有；最后一个对象归还后，才摘掉 slab 缓存节点、清理标记，并调用底层 free_pages 还页。大对象则核对返回位置和头部信息，直接归还整段。

    对应代码：slub.c 的 `kfree`。如果需要归还页面，或者调用者直接释放原先申请的页面，就进入下一步。

13. **归还物理页，并把它重新组织成可申请的空闲块。**

    页面回收进入 `pmm_mark_free` 时，先验证整个范围均属于合法已分配页，再修改状态，避免处理到一半才发现非法页。确认后清理分配标志、旧跨度等记录，为重新加入空闲结构做准备。Fit 允许分批归还已分配页面，但不能据此继续把已部分释放的原分配当作完整块使用。

    Fit 再把块按地址插回链表。前邻居末端正好接当前起点，才能向前合并；当前末端正好接后邻居起点，才能向后合并。若先向前合并，当前块头要改成前块头，再继续检查后面。被吸收的旧块头要摘链并取消块头身份，最终只留下一个完整块头。

    归还使空闲页总量增加，合并只改变这些页如何组块，不能再次增加数量。地址链表相邻也不代表物理连续，因为中间可能隔着仍在使用的页。合并完成后，更大的连续请求才可能重新得到满足。

    Buddy 回收则先核对原始请求、块头和实际跨度，再找真正的伙伴。伙伴来自同一个父块的左右拆分，不是任意相邻块；代码用物理页号 XOR 阶对应的位来定位，并检查范围、空闲标志和同阶条件。成功就合为更高阶继续查，直到不能合并，再挂回相应阶链表。

    **至此，资源从空闲结构交给使用者，又回到空闲结构，完成一次闭环。**普通资源不足应返回失败，非法指针、重复归还或错误长度则应被相应检查拒绝。

    对应代码：pmm.c 的 `pmm_mark_free`，default_pmm.c 的 `fit_free_pages、insert_block`，buddy_pmm.c 的 `buddy_free`。

14. **检查分配与回收的结果，证明资源状态在整个闭环中正确。**

    自测不是只看申请有没有返回。初始化检查要确认保留区不进入分配器、描述符与物理页对应正确；策略检查要构造不同候选块，确认算法确实选中应选的块；回收检查要确认空闲数量恢复，而且原本可以组成的大块确实重新出现。

    测拆分合并时，要先占住其他空闲页，只留下目标区域。否则“回收后还能申请大块”可能只是拿到了别处的大块，不能证明目标块合并正确。Buddy 同样需要隔离区域，分别验证非伙伴不能合并、伙伴可以逐级恢复。

    另用独立占用记录检查区间重叠，在存活分配中写不同数据，检查后续操作有没有覆盖旧内容。SLUB 要检查规格边界、跨页申请、交错归还、对象对齐和最后还页。非法操作独立运行，必须命中指定的预期检查，不能把任意崩溃、超时都当成成功拦截。

    这些行为应先写进规格，再分别生成实现和测试方案。AI 生成的测试也可能沿用实现的错误假设，所以还要用独立状态记录、数据校验和实际调试交叉验证。相关记录在 [prompt.md](prompt.md)、[testing.md](testing.md) 和 [ai-collaboration.md](ai-collaboration.md)。

    对应文件：[selftest.c](../code/kern/mm/selftest.c)、[run_tests.py](../code/tools/run_tests.py)。功能结果有了依据后，再观察内核启动和真实访存的执行过程。

15. **用启动检查和双 GDB，把程序行为对应到实际执行路径。**

    C 的启动 GDB 检查先确认固件进入物理入口，再等到高地址 C 入口检查 satp、栈、启动参数与映射。这样能区分“启动没有成功”和“断点地址设置错了”。当前分页前实际 PC 不等于高地址链接符号，旧脚本曾因此一直等待，修正断点后才能看到真实启动过程。

    双 GDB 再追踪一次真实访存。客户机 GDB 看 RISC-V 指令及其目标虚拟地址；宿主 GDB 调试 QEMU 进程，按这个目标设置条件断点，看模拟器如何处理。宿主暂停时模拟机器也停住，所以客户机等待不一定是内核卡死。

    宿主先观察 QEMU 软件 TLB 的页标记检查，未命中才进入 RISC-V 翻译代码；页表遍历计算当前表项位置、读表项、检查权限，遇到叶子得到物理地址，再进行物理访问权限检查并回填软件 TLB。要排除 GDB 自己读内存引发的调试查询，才能证明看到的是 CPU 指令访问。

    对命中路径，还应单步确认它绕过了 miss 分支，不能只用“第二次没在查表函数停下”推断命中。当前 QEMU 的取指和数据访问有不同入口，不能把一条观察到的取指调用链当成所有访存的唯一入口。

    Bare 对比进一步说明：客户机不分页时，客户机虚拟地址直接对应相同物理地址，不读客户机页表；QEMU 仍可能使用软件 TLB 来加速定位宿主 RAM。因此要分清客户机虚拟地址、客户机物理地址、宿主内存地址，也要分清客体页表、QEMU 软件 TLB 与宿主 OS 页表。

    对应文件：[boot.gdb](../code/tools/boot.gdb)、[qemu_mmu_debug.py](../code/tools/qemu_mmu_debug.py)、[qemu_host.py](../code/tools/qemu_host.py)。源码调用链和现场在 [gdb-mmu.md](gdb-mmu.md)，执行命令在 [操作流程.md](操作流程.md)。

    这些证据覆盖当前启动映射、内存发现、页与对象分配及回收。验证为项目自建测试；通用动态页表修改、多进程地址空间、按需调页和换页等尚未在当前实现中展开。
